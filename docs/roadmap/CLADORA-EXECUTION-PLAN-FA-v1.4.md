# برنامه اجرایی یکپارچه CLADORA

نسخه 1.4 برای چهار ورک توسعه

تاریخ تدوین ۸ اکتبر ۲۰۲۶ | وضعیت سند ابلاغی بر اساس تأیید کارفرما

این سند برنامه واحد توسعه Core و Operations، AIRPROP، SERVICE و Community & Experience است. معماری Workspace محور، مدیریت مالک چندواحدی و ترکیب مستقل قابلیت‌ها را به بسته‌های قابل تحویل و آزمون تبدیل می‌کند. بخش ویژه Community، دامنه کامل سند اولیه و ۱۲۲ قابلیت آن را حفظ و به مراحل اجرایی نگاشت می‌کند.

این نسخه جانشین برنامه v1.3 در موضوعات تحت پوشش است و موتور مستقل ارزش‌گذاری AIRPROP را به آن اضافه می‌کند؛ جانشین کل معماری CLADORA، بسته چرخه عمر v1.1 یا دستور تجربه کاربری v1.0 نیست. سوابق اجرا، قراردادهای معتبر و شناسه‌های موجود حفظ می‌شوند.

| ورک مخاطب | مسئولیت اصلی |
| --- | --- |
| CLADORA 12 | Core، اختیار، Workspace، منابع، ترکیب محصولات، سبد مالک و Operations |

| SERVICE CLADORA 02 | تعریف و عرضه خدمت، درخواست، پیشنهاد، سفارش و تحویل خدمت |
| CLADORA Community & Experience 01 | جامعه، رویداد، راهنما و هماهنگی تجربه با مصرف قراردادهای مشترک |

### تصمیم اجرایی این نسخه

با ابلاغ این نسخه، هر چهار ورک سند کامل را دریافت می‌کنند و فقط تسک شماره‌دار مربوط به خود را آغاز می‌کنند. تأیید این برنامه به معنی مجوز خودکار Push، migration عملیاتی، merge یا انتشار نیست؛ حدود مجوز ثبت‌شده هر اقدام همچنان معتبر است.

این ورک مسئول جمع‌بندی و گزارش به کارفرماست. ابلاغ اصلاحات و تصمیم‌های بین ورک‌ها توسط کارفرما انجام می‌شود. گزارش‌های وضعیت منابع ورودی‌اند و به‌جای اجرای مستقل آزمون در این سند محسوب نمی‌شوند.

### تغییرات اصلی

۱. مالکیت Community و Event از تخصیص کلی قدیمی به Core جدا شده است؛ CE مالک فرایند دامنه و Core مالک اختیار و زیرساخت مشترک است. CE010/011/012 قابلیت مستقل‌اند؛ بسته‌بندی و فروش آن‌ها با PC01 است.

۲. اولویت‌های P0/P1/P2 سند اولیه به موج‌های اجرایی این نسخه تبدیل شده‌اند. قرارداشتن قابلیت در پیوست به معنی پیاده‌سازی یا تعهد انتشار آن در مرحله اول نیست.

۳. وابستگی DW01A به تکمیل کل PC01 و وابستگی درخواست عمومی خدمت به PF01 حذف شده است. Work Order و Booking فقط وقتی نیاز واقعی دارند به خدمت متصل می‌شوند.

۴. «کد آماده»، «آزمون ایستا»، «آزمون واقعی دیتابیس»، «جریان کامل کاربر» و «انتشار» جدا ثبت می‌شوند. تعداد assertion معیار کافی برای قبولی نیست؛ نتیجه اجرای همان نسخه لازم است.

### قاعده رفع تعارض اسناد

در موضوع تقسیم کار و توالی اجرا، این نسخه مرجع جدید برنامه مصوب است. تعارض با قرارداد اجراشده یا تغییر معنای حق معتبر باید به‌صورت تصمیم نسخه‌دار ثبت شود؛ مستند جدید مجوز بازنویسی تاریخ یا تغییر ضمنی قرارداد نیست.

## ۲ معماری Workspace و منابع قابل تعریف

Workspace زمینه همکاری، پیکربندی و اختیار است. ساختمان، واحد، اتاق، زمین، خودرو، انبار، جای پارک، دستگاه و تجهیزات منابع آن زمینه‌اند. یک منبع هویت پایدار دارد و در صورت وجود رابطه مجاز می‌تواند به بیش از یک Workspace متصل باشد؛ این اتصال دسترسی خودکار بین آن‌ها ایجاد نمی‌کند.

| مفهوم | قاعده معماری |
| --- | --- |
| نوع Workspace | تعریف‌پذیر، توصیفی و نسخه‌دار؛ قالب شروع و واژگان پیشنهادی است، نه سقف قابلیت. |
| Resource | شناسه canonical، نوع و نسخه، ویژگی‌های لازم و روابط معتبر؛ بدون کپی هویت برای هر محصول. |
| Party | شخص، سازمان یا شرکت؛ با حساب ورود یکسان فرض نمی‌شود. نماینده در حدود رابطه معتبر عمل می‌کند. |
| Relationship | مالکیت، اجاره، مدیریت، بهره‌برداری، عضویت و نمایندگی مستقل با محدوده و اعتبار زمانی. |
| Capability | توانایی قابل فعال‌سازی؛ به‌تنهایی اختیار اجرای action را به کاربر نمی‌دهد. |
| Product و Pack | محصول تکی، ترکیبی یا مجموعه کامل؛ قرارداد و نسخه بسته در PC01 مدیریت می‌شود. |
| Service و Experience | خدمت دارای ارائه‌دهنده و اجرای مشخص؛ تجربه می‌تواند چند اقدام دامنه‌های مستقل را هماهنگ کند. |

### دامنه انواع و کاربری‌ها

مسکونی، شهرک ویلایی، تجاری، مرکز خرید، اداری، صنعتی، کارگاهی، لجستیک، انبار، هتل، اقامتگاه، مرکز خودرو، آموزشی، درمانی، ورزشی، فرهنگی، عمومی و کاربری مختلط، نمونه قالب‌اند. نوع سفارشی و ترکیب چند کاربری باید قابل تعریف باشد. فعالیت‌های تخصصی تابع پیش‌نیازهای واقعی خود هستند؛ نام نوع به‌تنهایی موجب منع نمی‌شود.

Workspace، منابع و تنظیمات از زمان شکل‌گیری هویت تا خروج مسئولانه و نگهداری سوابق مجاز دنبال می‌شوند. پیش‌فروش، تحویل جزئی، اجاره، فروش مجدد، تعمیر و تغییر مدیریت می‌توانند هم‌زمان یا تکرارشونده باشند. مدیریت اجرایی کارگاه ساخت خارج از دامنه فعلی باقی می‌ماند.

## ۳ ترکیب محصولات و مالک چندواحدی

### ترکیب قابل انتخاب

مشتری می‌تواند یک قابلیت، چند قابلیت یا مجموعه کامل را دریافت کند. وابستگی فنی به Core نباید به الزام خرید محصول نامرتبط تبدیل شود. Community بدون Event، Event بدون Community و Guide بدون SERVICE قابل فعال‌سازی‌اند. منوی کاربر از ترکیب قابلیت فعال و اختیار مؤثر ساخته می‌شود.

چهار تصمیم جدا هستند: حق قراردادی یا entitlement، فعال‌سازی Workspace، صلاحیت منبع برای خدمت و اختیار شخص برای action. منع یک action یا یک منبع به ممنوعیت کل محصول تعمیم داده نمی‌شود.

### حفظ حقوق فعلی

۳۶ entitlement فاقد contract_id طبق گزارش مبنا legacy_unprovenanced هستند؛ این عدد شمارش زنده جدید نیست. حقوق معتبر طبق قواعد موجود ادامه می‌یابد. اتصال حدسی، قطع جمعی یا تجمیع عمومی sum/max مجاز نیست. تصمیم هر مورد می‌تواند حفظ legacy، اتصال با مدرک، جایگزینی رو به آینده، انقضای تأییدشده یا disputed_hold باشد.

قواعد boolean، سقف عددی، scope، بازه اعتبار و explicit deny جدا تصویب و با evaluator رسمی اجرا می‌شوند. سوابق تصمیم و امضا به عامل واقعی زمان اقدام منتسب می‌مانند.

### سبد مالک حقیقی یا حقوقی

یک شخص یا شرکت می‌تواند مالک چند واحد، ساختمان یا منبع در چند Workspace باشد و شخصاً یا از طریق مدیر مجاز آن‌ها را اداره کند. نمای سبد تجمیعی است؛ عملیات و داده در مرجع اصلی باقی می‌ماند. مشاهده مالکیت مساوی عضویت اجتماعی یا مدیریت کل Workspace نیست.

| نیاز مالک | مرجع مسئول |
| --- | --- |
| منابع و روابط مالکیت و اختیار | Core و PF01؛ نمایندگی و واگذاری محدود و زمان‌دار |
| اجاره و فروش و مأموریت مدیریت | AIRPROP جریان تجاری؛ Core مالک ثبت رسمی رابطه و اختیار |
| شارژ و دریافت و پرداخت | Finance؛ تفکیک دفتر خصوصی مالک از دفتر رسمی Workspace |
| تعمیر و نگهداری و خدمات | Operations برای اجرای فنی؛ SERVICE برای سفارش و تحویل |
| Community و مزایا و تجربه | CE و مالکان تخصصی؛ عضویت و صلاحیت هر Workspace جدا ارزیابی شود |

### قاعده گزارش مانع

نبود محیط DB فقط آزمون DB و اتصالات وابسته را متوقف می‌کند. توسعه مستقل schema، قرارداد، adapter، domain و UI ادامه‌پذیر است. تست ساختاری جای pgTAP یا E2E نیست. اگر مسیر آزمایشی موجود قابل استفاده نیست، ورک نام دقیق مرحله و نیاز دسترسی را گزارش می‌کند؛ ایجاد پروژه جدید یا اتصال به Production راه‌حل خودکار نیست.

### مسیر بحرانی و کارهای موازی

DW01A و C01–C03 مسیر اتصال CE011 را باز می‌کنند. DW02 حداقلی مسیر انتخاب منبع SERVICE و AIRPROP را باز می‌کند. تکمیل PC01 به‌عنوان محصول تجاری یا PF01 کامل، شرط آغاز این مصرف‌کنندگان نیست. طراحی COM01 و FIN01 باید هم‌زمان با فرمان‌های نیازمند پیام یا پول انجام شود، نه پس از پایان کل دامنه.

BK01 یک قرارداد ظرفیت/زمان مشترک است؛ SERVICE Booking، ثبت‌نام ظرفیت‌دار Event و رزرو تجاری AIRPROP فرایندهای مستقل‌اند. Event پایه فقط علاقه و حضور دستی دارد و به BK01 وابسته نیست.

### گیت‌های پذیرش

G0 تطبیق وضعیت و دامنه؛ G1 قرارداد و مالکیت؛ G2 کد و آزمون جزء؛ G3 دیتابیس/امنیت/هم‌زمانی در صورت نیاز؛ G4 جریان مرورگر تا ذخیره و بازیابی؛ G5 مجوز و انتشار با کنترل سلامت. عبور از یک گیت برای یک برش به معنی پذیرش کل محصول نیست. تاریخ تقویمی پس از اعلام ظرفیت و دسترسی هر ورک تعیین می‌شود؛ در این سند زمان قطعی ساختگی تعیین نشده است.

ترتیب توسعه Core: ابتدا تغییر DW01A و قراردادهای حداقلی مصرف‌کنندگان؛ هم‌زمان طراحی شکاف DW01B/DW02/PC01؛ سپس projection PF و adapter Operations. COM/FIN طبق نیاز واقعی فرمان‌ها جلو می‌روند. BK01 پس از تصمیم معنای تعارض و نخستین مصرف‌کننده وارد اجرا می‌شود.

قرارداد snapshot موجود باید context_id و workspace_id صریح داشته باشد. کنترل افشا از اختیار مؤثر جاری مصرف شود. پنهان‌بودن reference باید در تمام پاسخ از جمله restrictions برقرار بماند. resolver هویت جای evaluator مجوز را نمی‌گیرد.

### اقدامات و خروجی

۱. شاخه، commit و فایل‌های آماده DW01A را با baseline همان ورک تطبیق دهید؛ اختلاف‌ها را ثبت و کار قبلی را حفظ کنید. evaluator رسمی و افشای کل پاسخ را بررسی کنید. ۲۵ assertion پیشنهادی فقط با log اجرای واقعی پذیرفته می‌شوند.

۲. C01–C03 و DW02 حداقلی را با نسخه، نام، schema، خطا و حداقل مصرف‌کننده تحویل دهید. PC01 در این برش نگاشت قابلیت به حقوق/فعال‌سازی جاری را روشن کند؛ بسته‌بندی کامل تجاری مانع این خروجی نیست.

۳. adapter منبع باید شخص/سازمان و چند Workspace را پوشش دهد. سپس projection اولیه PF و mapping اقدامات طراحی/آماده شود؛ دفتر مالی و هویت جدید ایجاد نشود.

۴. آزمون DB را در مسیر ایزوله موجود و مجاز مخزن اجرا کنید. اگر دسترسی موجود نیست، فقط همان بخش را مسدود ثبت و adapter و قراردادهای مستقل را ادامه دهید. endpoint DW01A بعد از پذیرش RPC آماده اتصال است.

## ۱۵ ابلاغ شروع SERVICE

درج missing با صفر یکسان نیست. واحد پول، تاریخ مؤثر، دوره اجاره و مبنای مساحت باید صریح باشد. هزینه پارکینگ یا اثاث، مالیات و کارمزد از مبلغ پایه تفکیک شود؛ تبدیل ارز با نرخ و تاریخ ثبت‌شده انجام گیرد.

منابع در registry نسخه‌دار ثبت می‌شوند: مالک، روش دریافت API/feed/import/دستی، شرایط مجاز مصرف و بازنشر، دوره تازگی، خطا و کیفیت. خرید داده، اتصال پولی یا برداشت بدون مجوز جزو ابلاغ نیست. Connector هر منبع پس از احراز دسترسی و قرارداد آن ساخته می‌شود.

مقایسه منابع چند Workspace فقط از داده عمومی/دارای مجوز یا اشتراک صریح ممکن است. عضویت در یک Workspace اجازه استفاده از سوابق خصوصی دیگری برای آموزش یا نمایش نمونه مقایسه‌ای نمی‌دهد.

### وضعیت‌های پیشنهادی

requested، collecting، insufficient_data، calculated، review_required، reviewed، superseded و failed. این وضعیت‌ها دامنه پیشنهادی قراردادند؛ پیش از اجرای پایدار به schema رسمی تبدیل می‌شوند. مسیر insufficient_data خروجی معتبر سامانه است و نباید با عدد ساختگی پر شود.

Job طولانی async با request id و receipt، idempotency و retry محدود اجرا شود. غیرفعال‌شدن منبع داده یا لغو دسترسی، خواندن/انتشار بعدی را محدود می‌کند؛ نگهداری تاریخچه تابع سیاست مجاز همان داده است.

## ۲۳ روش مدل و اعلام نتیجه قابل توضیح

### Baseline و مدل‌های قابل تکامل

نسخه اول بر شواهد مقایسه‌ای استانداردشده و تعدیل‌های نسخه‌دار تکیه کند. مدل آماری یا یادگیری ماشین فقط پس از وجود داده کافی و backtest اضافه شود. وزن عوامل یا ضریب طبقه و امکانات ثابت و سراسری فرض نشود؛ بر حسب نوع منبع و بازار کالیبره شود.

سابقه خرید با تاریخ و شرایط آن یک شاهد است. تورم، شاخص ملک، نرخ ارز و اجاره عوامل متفاوت‌اند؛ رشد قیمت خرید با تورم به‌تنهایی مدل ارزش‌گذاری نیست. تعدیل زمانی بر اساس شاخص‌های هم‌پوشان نباید دوبار اعمال شود. ارتباط آماری با اثر علّی یکسان تلقی نشود.

مدل فروش از داده فروش و مدل اجاره از داده اجاره استفاده کند. روش درآمدی برای نوع منبع مناسب می‌تواند مکمل باشد، با فرض خالی‌ماندن، هزینه، دوره و نرخ روشن. تبدیل فروش به اجاره با یک ضریب دلخواه یا تعمیم مدل مسکونی به انبار مجاز نیست.

### ساختار دامنه پیشنهادی

Source، Observation، Comparable Set، Model Version، Valuation Run، Result و Review موجودیت‌های دامنه AIRPROP هستند. Resource و Party و نقش یا دفتر مالی مجدد ساخته نمی‌شوند. ذخیره raw data با سیاست مجوز و retention؛ نتیجه مشتق نیز باید کنترل افشا داشته باشد.

### امنیت و مصرف

اختیار درخواست، دیدن نتیجه، دیدن شواهد، review و تغییر قیمت عرضه جدا طراحی شود. capability فعال مساوی اختیار نیست. PF فقط نتیجه منابع مجاز را جمع‌بندی می‌کند. CE فقط خلاصه مجاز را در تجربه مربوط نشان می‌دهد؛ دیدن خلاصه، حق دیدن سوابق معامله یا مالک را ایجاد نمی‌کند.

Idempotency با actor/context/workspace/resource و fingerprint ورودی مقید شود؛ خواندن replay دوباره با اختیار جاری بررسی شود. تغییر واحد، purpose یا تاریخ با همان کلید پذیرفته نشود. ثبت مالی از valuation مجاز نیست؛ FIN01 فقط مرجع عملیات مالی مستقل است.

### آزمون‌های لازم

VAL01 واحدهای یک ساختمان با طبقه/مساحت/امکانات متفاوت؛ VAL02 ask در برابر deal؛ VAL03 آگهی تکراری چندسایتی؛ VAL04 ارز و basis متراژ و دوره اجاره؛ VAL05 داده ناکافی/کهنه/پرت؛ VAL06 عدم تعدیل زمانی دوباره؛ VAL07 تاریخ انتشار شاخص و جلوگیری از استفاده از اطلاعات آینده.

VAL08 backtest زمانی و مکانی بدون نشت واحد تکراری بین train/test؛ VAL09 گزارش MAE یا median absolute percentage error همراه bias و پوشش بازه به تفکیک نوع/منطقه؛ VAL10 reproducibility نسخه مدل و snapshot؛ VAL11 override نسخه‌دار و لغو اختیار؛ VAL12 منع نشت cross-tenant و شواهد محدود؛ VAL13 retry/هم‌زمانی؛ VAL14 عدم تغییر خودکار Listing یا journal.

### گیت پذیرش واقعی

آزمون روی داده ساختگی صحت منطق را نشان می‌دهد، نه دقت بازار. دقت واقعی فقط با داده مجاز نگه‌داشته‌شده برای ارزیابی و benchmark ساده گزارش شود. آستانه‌ها پیش از ارزیابی نهایی قفل شوند؛ بازار کم‌داده جدا گزارش شود. انتشار مدل جدید نیازمند مقایسه با نسخه قبلی، کنترل drift و rollback نسخه مدل است.

تا تحویل منابع داده و معیار دقت، وضعیت AP-VAL-01 «در طراحی و آماده‌سازی» است. این عدم قطعیت مانع عرضه موجود، DW01A، SERVICE یا CE پایه نیست. مالک AIRPROP در تحویل اول یک بازار و نوع منبع برای baseline پیشنهاد می‌کند؛ انتخاب تأییدنشده به‌عنوان تصمیم قطعی ثبت نشود.

هر ورک هنگام شروع، نسخه مصوب سند و commit مرجع را ثبت می‌کند؛ واژه latest به‌تنهایی کافی نیست. سند آماده ولی ادغام‌نشده با ref شاخه/commit مشخص مصرف می‌شود و به‌عنوان main معرفی نمی‌شود. تغییر قرارداد مشترک همراه impact بر مصرف‌کنندگان، سازگاری و approval ثبت شود.

همه دسترسی به مرجع مشترک دارند؛ مجوز ویرایش/تأیید از خواندن جداست. main با PR به‌روزرسانی شود. تاریخچه حذف نمی‌شود و نسخه منسوخ برچسب superseded می‌گیرد. manifest آغازین فقط اسناد واقعاً موجود/بازیابی‌شده را قطعی معرفی می‌کند؛ فایل‌های محلی ورک‌ها تا تحویل با وضعیت pending_delivery ثبت شوند.

## ۲۹ چرخه شروع اتمام و بازگشایی

| وضعیت یا فرمان | شرط انتقال و اثر |
| --- | --- |
| planned به ready | scope، مالک، معیار پذیرش و baseline مشخص؛ وابستگی لازم روشن |
| ready به in_progress | مسئول مجاز شروع را ثبت کند؛ started_at و شماره چرخه ثابت شود |
| in_progress به in_review | کد/سند و evidence به commit همان چرخه متصل؛ نقص‌های شناخته‌شده ثبت |
| in_review به tested | همه تست‌های الزامی قابل اعمال واقعاً پاس؛ N/A با دلیل و تصمیم مجاز، نه حذف خودکار |
| tested به accepted | داور مجاز معیارها و evidence همان نسخه را تأیید کند؛ تغییر کد بعد از آزمون نیازمند ارزیابی اثر |
| accepted به closed | رسید اتمام صادر و زمان/محدوده ثبت؛ انتشار شرط جدا طبق تعریف بسته |
| reopen یا request_change | دلیل و scope اصلاح ثبت؛ چرخه تازه planned/ready با parent_cycle ساخته شود؛ چرخه بسته قبلی دست‌نخورده |
| blocked و cancelled | blocked برچسب مانع مستقل از مرحله؛ cancelled با دلیل و اختیار، نه closed موفق |
| release | وضعیت جدا not_released/ready/deployed/verified/rolled_back؛ closed لزوماً deployed نیست |

یک بسته می‌تواند چرخه قبلی بسته و چرخه اصلاح جاری فعال داشته باشد؛ داشبورد هر دو را روشن نشان می‌دهد. شکست جدید اعتبار قبلی را حذف نمی‌کند، بلکه invalidated یا superseded شدن evidence برای محدوده جدید با رویداد جدا ثبت می‌شود.

هر command با request id، idempotency و expected-version اجرا شود. انتقال هم‌زمان فقط یک نتیجه معتبر بدهد. درج داده، transition و audit/receipt باید اتمیک باشد. webhookهای CI/PR ورودی evidence هستند؛ سبزشدن CI یا merge به‌تنهایی مجوز auto-close نیست. callback تکراری یا قدیمی نباید وضعیت را عقب ببرد.

GitHub مرجع کد/سند/PR است؛ دیتابیس PM مرجع چرخه، وضعیت و پذیرش. Issue/Project احتمالی projection پیوندشده با شناسه package/cycle است، نه مرجع وضعیت رقیب. تا PM runtime آماده نیست، گزارش نسخه‌دار دستی منبع موقت است و هیچ داشبورد زنده ساختگی معرفی نمی‌شود.

## ۳۰ ابلاغ PM و استاندارد UX و CSS

### تسک V14 CORE PM01

Core ابتدا inventory قابلیت‌های موجود، مدل منطقی بخش ۲۸، state machine بخش ۲۹ و قرارداد command/receipt را آماده کند؛ سپس برش محدود ثبت package/cycle/evidence/acceptance طراحی و در محیط مجاز آزموده شود. PR مستندات این نوبت هیچ migration یا runtime PM ایجاد نمی‌کند. این مسیر قرارداد DW01A و C01–C03 را متوقف نکند.

### تعهد هر چهار ورک

شناسه بسته و چرخه، baseline اسناد، commit و آزمون را در تحویل درج کنید. برای اتمام درخواست closure با evidence بدهید. برای تغییر بسته بسته‌شده، change request متصل به چرخه قبلی ثبت کنید. هیچ تست اجرا‌نشده pass و هیچ قابلیت منتشرنشده production ثبت نشود.

### مرجع UI و UX و CSS

Core مالک الگو و tokens مشترک؛ هر ورک مالک صفحه‌های دامنه خود است. رنگ، تایپوگرافی، فاصله، breakpoint، حالت loading/empty/error/disabled، focus، فرم/جدول/منو، اعداد مالی، RTL و دسترس‌پذیری باید در فهرست مشترک به فایل و نسخه واقعی متصل باشند. CSS کپی‌شده یا hard-code جدید نیازمند دلیل و کنترل سازگاری است؛ این ابلاغ خودکار فایل‌های فعلی را تغییر نمی‌دهد.

تغییر token یا کامپوننت مشترک باید اثر روی چهار ورک، آزمون visual در RO/EN/FA و موبایل/دسکتاپ و مسیر migration مصرف‌کنندگان داشته باشد. اجزای جدید تا تصویب به‌عنوان proposed مشخص شوند؛ یک style guide جدید جایگزین بی‌بررسی تمام UIهای موجود نشود.

### آزمون پذیرش PM01

منع closure بدون evidence؛ منع self-approval طبق سیاست؛ رد stale version؛ چرخه جدید بدون حذف تاریخچه؛ رفع مانع بدون تغییر مرحله؛ حفظ نسبت evidence با commit؛ retry بدون transition تکراری؛ منع دسترسی غیرمجاز؛ webhook تکراری/قدیمی؛ گزارش زمان شروع/اتمام و اصلاح به تفکیک ورک.

### داشبورد نظارت مورد انتظار

برای هر بسته: وضعیت جاری، چرخه، مسئول، آغاز، آخرین تغییر، blocker، تست و پذیرش، لینک PR و وضعیت انتشار نمایش داده شود. درصد پیشرفت فقط با وزن مصوب و معیار معلوم گزارش شود؛ تعداد فایل یا commit شاخص تکمیل نیست. اصلاح و بازگشایی در گزارش تاریخچه آشکار باقی بماند.
