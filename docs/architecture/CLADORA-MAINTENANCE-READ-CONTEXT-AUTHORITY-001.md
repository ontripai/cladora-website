# Maintenance list and KPI context authority

The legacy SECURITY INVOKER request and work-order list gateways filtered property and unit but omitted building. Their KPI gateway counted all tenant payables, even when the requested context was narrower. RLS evaluated the JWT active context, which can be broader than the explicitly requested RPC context.

Actual authenticated CI exposed an additional integration defect: the invoker gateways tried reading work_orders, tickets and vendors after direct authenticated SELECT had deliberately been revoked. Those table boundaries remain closed. The gateways delegate to one bounded read model owned by the existing cladora_rpc_owner role, which cannot log in, create objects, become superuser or bypass RLS. Only that internal role receives two missing SELECT grants (tickets and vendor_payables) and execution of the existing context verifier, which verifies authentication under its existing owner. The reader needs no Auth schema/table grant. Five role-specific RLS policies restrict domain rows and building/unit metadata to the verified explicit context and canonical authority, allowing a unit's own parent building. No role memberships, authenticated domain-table grants, module bindings or delegations are added.

The read model independently filters every row through a bounded boolean predicate for the explicitly requested RPC context. It verifies current caller-owned context, existing dedicated read permission, exact physical scope and canonical installed maintenance module authority. Privileged authorization metadata requires a SECURITY DEFINER predicate, which reads no maintenance/financial rows and returns only a boolean. Its allowlist contains requests.read and work_orders.read only; permission/authentication failures return false. It cannot delegate writes or financial posting, PUBLIC/anon cannot execute it, and the private canonical engine remains unavailable to authenticated callers. The internal reader allowlists three read views, repeats authentication and legacy/MFA verification, and joins vendor/payable projections within the same tenant.

Both payable KPI subqueries join the payable to its actual work order in the same tenant and apply the request-read predicate to that target. The existing summary permission contract and JSON keys are preserved. Hidden targets contribute neither count nor amount. Canonical module deactivation produces empty lists/zero KPIs while legacy entitlement remains true. The three gateway signatures, execution grants and SECURITY INVOKER mode stay unchanged. RLS applies to the non-BYPASSRLS internal reader. After authenticating and verifying the caller-owned context, the reader sets a dedicated transaction-local context GUC for its RLS policies, restores its prior value on success/error and independently checks every result row. This never changes JWT identity or claims, does not rely on custom active-scope JWT fields and cannot authorize access by itself: predicates reverify caller/context, tenant and canonical target permission, while authenticated cannot assume the reader role or SELECT the closed tables. Work-order reads still require AAL2; request/summary reads retain existing caller verification policy.

Isolated pgTAP tests run the gateways as authenticated, first with intentionally broader legacy JWT scope fields and then a standard JWT without those fields. Distinct property, building and unit fixtures prove exact list counts, returned identifiers and financial amounts; foreign tenant fixtures prove exclusion. Tests cover status/pagination, deactivated canonical module, expired context, authentication/MFA, predicate permissions, private-engine ACLs, closed authenticated tables, reader ownership/no role membership/no schema CREATE/no Auth table access, transaction-scope restoration on success/error, read-view allowlist and no mutation side effects. Draft journals/payables are read-test fixtures only, not evidence of real posting. Every test rolls back.

This change covers list_maintenance_requests_v1, list_work_orders_v1 and get_maintenance_summary_v1. The separate get_maintenance_v1/get_customer_maintenance dashboard projection and ticket/RFQ creation routes are not changed. Work order 74 and live financial data are not modified.
