# Communications private-message subject provider v1

`communications-private-message-subject-provider.v1` resolves an existing private message for a transaction-scoped consumer. Communications remains the canonical owner of the message and participant state. Core remains the owner of current authority and the transaction host. The provider creates no message copy, authority projection, receipt ledger, audit store, outbox, or idempotency store.

The existing `communications.private_messages` row now carries a positive safe-integer `version` and a canonical `lifecycle_state` of `available`, `quarantined`, or `deleted`. Existing rows start at version 1 and `available`. Message identity is immutable. A body or lifecycle change must advance the version by exactly one; a version cannot change without one of those revisions. Physical deletion is forbidden, so delete/reinsert cannot reset version history or move an identifier to another Workspace.

`communications.resolve_private_message_subject_v1` is a stable, `SECURITY DEFINER` resolver with execution revoked from public application roles, including `service_role`. The Core transaction host owns invocation through its trusted database scope; this package adds no grant or runtime wiring. The resolver requires the actor already bound by Core authority to equal `auth.uid()`. The message unit must resolve through exactly one current `platform.workspace_property_bindings` row to the requested active Workspace. `native_workspace_scope_for_membership_v2` must bind the same current membership to that Workspace, and `check_workspace_native_permission_v2` must confirm the current `communications.feed.read` permission and Communications module. Acceptance additionally requires a current canonical Workspace role assignment whose Communications permission/module covers the exact message unit; a scoped deny wins. A base membership role, physical context, or participant row cannot provide fallback authority. Missing, ambiguous, cross-Workspace, cross-scope, revoked, or unauthenticated requests share one bounded denial.

An accepted SQL result contains only the decision, message identifier and version, exact Workspace, lifecycle, and two booleans describing whether the calling participant is current or revoked. Expected stale, scope, lifecycle, and participant denials return one bounded decision row with all source fields null, so the surrounding transaction remains usable and performs no write. It never returns the body, sender, conversation, unit, membership identifier, profile, or another participant. A real PostgreSQL serialization failure remains an exception for the Core host's fresh-transaction retry loop.

## Request-party audience gate

`communications.resolve_private_message_request_audience_v1` is a separate private, unwired composition gate for a `service_request` aggregate. The existing subject provider must accept first. The gate then consumes `app_private.service_request_subject_context_v1` for the exact Request/version and reads the canonical SERVICE offering only to obtain its provider party. It compares the message-time audience with the canonical beneficiary/provider set through current `identity.membership_parties` or approved vendor-portal-to-vendor-party mappings. Both parties must be present; when beneficiary and provider identify the same party, one matching identity is sufficient. Missing, ambiguous, stale, revoked, cross-Workspace, one-sided, or unrelated mappings deny; membership roles and Workspace access cannot provide fallback audience authority.

The Core V2 consumption contract is `communications.private_message_request_audience`: `permission_code=services.orders.subject_link`, `module_code=services_orders`, `evaluation_purpose=service.request.subject_link`, `aggregate_type=service_request`, `aggregate_id=Request ID`, and `aggregate_version=resulting Request version`. The Request resolver receives `aggregate_version - 1` as its expected pre-mutation version. The message `subject_reference` uses kind `message`, relation `subject_link`, and equal version/request_version values. The SERVICE `services.orders.read` and Communications `communications.feed.read` checks remain separate canonical resolver gates. Accepted CE evidence has its own evidence identity and provider code rather than relabelling the base message evidence. Evidence remains status-only. Neither the SQL gate nor the TypeScript provider returns a party, participant, membership, conversation, unit, sender, or message body. There is no route, grant, SERVICE composition change, notification, durable write, or runtime activation in this package.

The TypeScript provider directly implements the merged `CoreTransactionProvidersV2` surface and emits `core-transaction-provider-evidence.v1`; it does not define a second evidence type. Its subject binding is `message` / `subject_link`, and it consumes the transaction-bound `core-current-authority-decision-receipt.v1`. Authority denial or any actor, Workspace, attempt, command, aggregate, or transaction mismatch is rejected before SQL. The only issued statement is the resolver `SELECT`. Quarantined, deleted, revoked, stale, missing, and cross-Workspace sources return bounded Core evidence with no reference metadata. Wiring this provider into SERVICE composition or a public route remains outside this package.

The optional Request-audience composition uses the canonical Core v2 transaction profile `services.orders.subject_link` / `services_orders` / `service.request.subject_link`. It binds the exact pre-mutation Request version and existing message reference, then accepts only an unambiguous current message audience containing both the Request beneficiary and offering provider. Disposable PostgreSQL coverage runs this provider through the real Core host for two-party and same-party acceptance, beneficiary-only and provider-only denial, unrelated or revoked participants, missing or ambiguous mappings, stale versions, cross-Workspace denial, exact replay, independent evidence identity, and retry of a propagated `40001`. Evidence remains status-only and excludes message content and audience identities.
