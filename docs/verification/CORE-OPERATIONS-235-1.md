## Command contract and failure behavior

The browser snapshots and validates one exact JSON wire before dispatch, then creates
one UUID key and SHA256 UTF8 fingerprint. No trimming/coercion/NUL/invalid-surrogate
rewrite is permitted after snapshot; lowercase identifiers, dates, template checklist,
revision/every/text/cost bounds are validated before in-memory pending admission.
Server recomputes the exact wire digest; SQL independently validates input and derives
actor/tenant/Workspace/Context/membership/role/permission/resource from canonical
current Auth/Context helpers. No caller-supplied actor/authority/ticket or service role.
C03 request_hash includes that full reservation binding and wire; replay permits a
fresh authority revision only if the actual current tuple remains authorized.

Reserve commits only a status102 intent. Execute locks the same C03 row, calls the
existing domain function and commits mutation + domain audit + command audit + outbox
+ receipt together. A lost response is UNKNOWN. Bounded business rejection rolls back
its subtransaction and records a rejected receipt with no business/audit/outbox effect.
Timeout/cancellation/unlisted errors roll back, never success. Same-key replay returns
the canonical receipt without a second issue/audit; changed wire conflicts.

Actor+Workspace admission and resource fences reject new/next commands while unresolved.
Web Locks limit tabs; SQL locks are the cross-device authority. A legacy checklist
trigger takes the Workspace row lock before pending scan; deadlock victim/timeout rolls
back. Currentness/authority is checked after explicit waits and after the domain call,
before subsequent audit/outbox/receipt/response; invalidity aborts execution. Temporary
writes may occur inside a transaction then roll back. No strict logout/COMMIT
serialization is claimed; WAL/sequence effects and the final-check logout window remain.
Deferred/implicit waits and actual atomic rollback are PG execution gates, not proven
by the offline model.

Reload reconciles canonical C03 before new admission. A matching GET is only current
state. Strict receipt binding/result validation precedes ACK and local cleanup. A lost
ACK and subsequent command on another device resolves the older exact key first.
Malformed receipt, missing storage/Web Locks, current denial or uncertain reconciliation
keeps the gate closed; explicit retry uses only the saved key/body. Current permission
is mandatory to disclose a historical receipt; a receipt is not an authorization grant.
The full data-retention/deleted-storage/new-device/abandonment cases and two proposed
owner policy decisions are in `supabase/install/v14-operations/recovery.md` and manifest.
Those Operations policies are proposed, not inherited approval from CE/Building.
